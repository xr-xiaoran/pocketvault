# PocketVault 临时文件交接箱 学习与面试手册

哥哥，这份手册对应 github.com/xr-xiaoran/pocketvault。建议用你自己的临时文本文件练习，依次完成上传、去重、分享、耗尽、撤销和并发实验。重点是弄懂内容寻址、所有权、事务和有限次数凭证，不是把它称为已经服务大量用户的网盘。

## 1 项目场景和两处小设计

协会或小团队经常临时交接文件：同一份材料被多次上传，文件名不同但内容相同；分享链接发出去后，希望只允许有限次取走，并能主动撤销。PocketVault 为这个小场景实现文件存储和短时分享。

第一处小设计是“空间账本”：同一用户上传相同字节两次，生成两个文件记录，但只保存一份内容。统计接口同时显示逻辑字节数、物理内容字节数和节省字节数，面试时能直接演示去重效果。

第二处是“可撤销下载凭证”：创建分享时指定次数和过期秒数；每次被服务接纳的 GET 消耗一次。次数耗尽、已过期、已撤销都不再放行。不要理解成用户下载后文件会从世界上消失，也不能阻止已获得文件的人复制。

当前范围是每文件最大 4 MiB、每用户物理内容最多 64 MiB、最多 1000 个逻辑文件的单机学习项目。这里的小文件限制是实现边界，不是性能成绩。

## 2 从零运行

终端 A 进入项目目录：

```powershell
go version
go mod download
go test -count=1 -cover ./...
go vet ./...
$env:VAULT_KEYS='alice=alice-local-demo-key-12345,bob=bob-local-demo-key-123456'
go run ./cmd/pocketvault
```

终端 B：

```powershell
$env:VAULT_KEY='alice-local-demo-key-12345'
powershell -ExecutionPolicy Bypass -File ./scripts/demo.ps1
```

VAULT_KEYS 是服务端信任的身份配置，VAULT_KEY 是演示脚本使用的一个 key。它们名字不同，因为前者包含多个用户映射，后者只代表当前演示者。这里没有注册登录，没有 JWT；不应在简历上给本项目添加不存在的登录功能。

默认监听 127.0.0.1:8082；DB_PATH 不设置时自动创建 pocketvault.db。默认 key 只是示例。你可以生成自己的长随机值，但两个终端的配置必须相符。

demo 做两次相同内容上传、创建一次性分享、下载一次、验证第二次 410、展示空间统计。每次运行使用新的随机内容，避免受上一轮数据干扰。文件会保留，最多 1000 个文件后需通过 API 删除不需要的文件。

## 3 手动完成一个业务闭环

先建立请求头和上传字节：

```powershell
$h=@{Authorization="Bearer $env:VAULT_KEY"}
$bytes=[System.Text.Encoding]::UTF8.GetBytes('hello pocketvault')
$a=Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8082/api/files?name=notes.txt' -Headers $h -ContentType 'application/octet-stream' -Body $bytes
$a | ConvertTo-Json -Depth 6
```

响应中 file.id 是逻辑文件 ID，file.sha256 是内容摘要，size 是字节数，deduplicated 表示本次是否复用已有内容。再次用不同文件名上传相同 bytes，应得到不同 file.id、相同 sha256、deduplicated=true。

创建分享：

```powershell
$body=@{downloads=1;ttl_seconds=60}|ConvertTo-Json
$s=Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8082/api/files/$($a.file.id)/shares" -Headers $h -ContentType 'application/json' -Body $body
$url="http://127.0.0.1:8082/s/$($s.token)"
Invoke-WebRequest -UseBasicParsing -Uri $url
```

再次请求同一 URL 应返回 410。这里访问 share URL 不需要原用户 API key，因为 token 本身就是授权凭证。把 URL 交给谁，谁就可能使用它。浏览器插件或安全扫描器如果真的发 GET 也会花掉次数，不能把它误说成“精确允许一个人下载”。

统计和撤销：

```powershell
Invoke-RestMethod -Uri 'http://127.0.0.1:8082/api/stats' -Headers $h
Invoke-RestMethod -Uri 'http://127.0.0.1:8082/api/shares' -Headers $h
Invoke-RestMethod -Method Delete -Uri "http://127.0.0.1:8082/api/shares/$($s.id)" -Headers $h
```

列表不返回明文 token。创建分享时拿到 token 后应妥善保存；遗失时新建分享即可，服务端不能从摘要还原它。

## 4 从请求追到数据库

```text
上传请求 -> API key 映射 owner -> 限制读取 4 MiB
 -> 校验名字 -> SHA-256 内容摘要
 -> 事务插入或复用 blob -> 检查配额 -> 新建 file -> 提交

创建分享 -> owner 条件校验 file -> 生成随机 token
 -> 只保存 token 摘要与次数/过期时间

下载 -> 摘要查询 token -> 条件更新 remaining-1
 -> 在同一事务读取字节 -> 提交 -> attachment 响应
```

cmd/pocketvault/main.go 解析 VAULT_KEYS，拒绝短 key、重复 key 和重复 owner，避免身份歧义。internal/httpapi/api.go 处理身份、上传正文和 HTTP 头。internal/vault/store.go 负责原子数据操作。

目录虽小，但业务责任明确。Store 接收 owner 参数；owner 的可信来源在 API 层。直接调用 Store 的测试可以指定 alice/bob，这是测试准备，不表示真实客户端能伪造 owner。

## 5 Go 基础在这里怎样用

`[]byte` 表示原始字节序列，适合文件内容。string 也能保存字节，但文件不必是合法 UTF-8，因此正文按 bytes 处理。文件名则要求合法 UTF-8，且不能包含斜杠、反斜杠、换行或 NUL。

`io.ReadAll` 会把数据读入内存。这里只允许最大 4 MiB，因此采取简单的有界读入；它不是大文件流式上传。多个并发上传会消耗“并发数乘文件大小”的内存，大规模服务还要限制并发并改为流式方案。

`http.MaxBytesReader` 在 HTTP 层限制大小，Store.Put 再检查 len(data)，形成不同调用入口都能遵守的规则。不能只相信 Content-Length，因为客户端可能分块传输或发送错误长度。

`crypto/rand` 用于生成难以预测的 token；普通数学随机数适合模拟和退避，不适合授权凭证。`crypto/sha256` 用于内容摘要和 token 摘要，两者调用相同算法，但目的不同。

sql.Tx 是一组要一起成功或失败的 SQL 操作。事务没有跨文件系统边界，因此把 BLOB 放 SQLite 内部，便于初学者清楚验证原子性。将来迁移对象存储时，这个简化就不再成立。

## 6 三张表的职责

blobs 表的主键为 `(owner, hash)`，保存 data 和 size。相同用户、相同内容只能一份；不同用户保存相同内容也各自占一份，避免跨用户泄露“别人是否上传过该内容”。

files 表保存逻辑记录：id、owner、name、hash、size、created_at。两个名字可以指向相同 blob。文件 ID 与哈希不是一回事；修改文件名不应该改变内容地址，而上传修改过的内容会得到新哈希。

shares 表引用 file_id，保存 token_hash、remaining、expires_at、revoked。file_id 外键使用 ON DELETE CASCADE；删除逻辑文件时自动清除相应分享。删除某个逻辑文件不会影响另一个指向相同 blob 的逻辑文件。

时间使用 Unix 秒；TTL 取值 1-86400 秒，下载次数 1-100。若 expires_at 等于当前秒数，已经过期，必须拒绝。和 RetryLab 的毫秒字段不同，不能把两个项目的时间值直接混用。

## 7 去重怎样避免并发重复插入

上传首先计算 SHA-256，然后事务内执行：

```sql
INSERT INTO blobs(owner,hash,data,size)
VALUES(?,?,?,?)
ON CONFLICT(owner,hash) DO NOTHING;
```

数据库唯一约束解决两个请求同时上传相同内容的竞争。影响行数为 0，说明复用了已有 blob；为 1 则新建。随后在同一事务检查用户物理内容大小和文件数量，再插入 files。

为什么先写再查配额：SQLite 的 deferred 事务如果先读后写，多个连接可能同时持有读快照再尝试升级 writer，产生忙/升级失败。先执行写语句取得写事务，再查询配额和写元数据。超限时整体回滚，刚插入的 blob 也会撤销。

这里只做上传后的存储去重，不是“客户端只上传哈希就秒传”。上传完整字节才能由服务端验证内容地址，也避免把哈希存在性当成访问权限。SHA-256 理论上仍可能碰撞；当前采用常见的密码学碰撞可忽略假设，没有实现逐字节碰撞分桶。

## 8 空间账本怎样计算

例如内容长度为 100 字节，alice 上传两次：files=2、blobs=1、logical_bytes=200、physical_bytes=100、saved_bytes=100。再传一份 50 字节不同内容，逻辑总计 250、物理内容总计 150。

physical_bytes 表示现存 blob 的内容长度总和，不是 Windows 资源管理器显示的 .db 文件大小。数据库索引、页面、WAL 日志、空闲页都会占磁盘。删除 blob 后统计下降，.db 不一定马上缩小，这不代表删除失败。

Stats 使用一条 SQL 获取四项子查询结果，减少分开查询期间插入/删除导致不同时间点统计混合的问题。saved_bytes 等于 logical_bytes 减 physical_bytes。

在面试中展示这个例子比写“空间节省 50%”更准确。这个 50% 只适用于两份完全相同内容的示例，不是所有用户数据都能节省一半。

## 9 分享凭证为什么只存哈希

token 由 32 个安全随机字节组成，十六进制编码后长 64 个字符，随机性仍是 256 位，字符数增加不等于熵增加。返回原文 token 给创建者，数据库只保存 SHA-256(token)。

这样数据库表泄露时，攻击者不能直接把 token_hash 复制到下载 URL 使用，因为服务会再对输入做一次哈希。安全基础是 token 本身具有高熵；弱密码不能用“直接 SHA-256”代替 bcrypt/Argon2。

明文 token 仍会出现在分享 URL，可能进入浏览历史、代理日志和聊天记录。本项目不写访问 URL 日志，响应设置 no-referrer、no-store；真实部署还要 HTTPS、日志脱敏和权限管理。数据库内容没有加密，不能把哈希存 token 说成文件已加密。

## 10 并发限次下载的正确做法

错误思路：先 SELECT remaining，if remaining>0 就返回文件，然后 UPDATE remaining-1。两个请求都可能看见 remaining=1，最终放行两次。

实际代码先执行原子条件扣减：

```sql
UPDATE shares SET remaining=remaining-1
WHERE token_hash=? AND revoked=0
  AND expires_at>? AND remaining>0
RETURNING file_id;
```

没有返回行，统一表示不存在、过期、撤销或耗尽，API 返回 410。返回 file_id 后在同一事务读取 bytes，再 Commit；数据库查询失败时回滚，次数不会丢失。

HTTP 写入发生在 Commit 之后。如果网络断开，数据库已经扣了一次。项目明确定义额度是“获准 GET 的次数”，不是“完整下载成功的次数”。没有可靠客户端确认协议时，服务端无法知道用户是否完整收到并保存了文件。自动补回次数还可能让恶意断连者无限获得数据。

因此成功条件是数据库放行次数不超额度，测试的 40 争 3 正是在验证这一点。它不能证明互联网传输 exactly-once，也不证明只会有 3 个不同的人看过文件。

## 11 HEAD Range 撤销和删除的细节

Go 的 GET 路由也可能匹配 HEAD。本项目在下载 handler 里检查 Method，只允许 GET，否则 405，确保探测请求不会悄悄扣次数。

Range 断点请求返回 416，不消耗次数。因为一次完整文件下载可能变成多个分段请求，必须先定义“次数按请求还是按会话”。当前选择简单规则，不支持断点续传。

撤销将 revoked 设为 1，而且要校验 share 所属 file 的 owner。重复撤销仍然安全。撤销先于后续下载事务完成时，后续会被拒绝；已在撤销之前成功获得授权并读取了 bytes 的请求仍可能完成发送。

删除 files 采用 owner 条件，拿到 hash 后检查是否还有其他引用；没有时删除 blob。files、shares、blob 的变化在同一数据库事务内完成。不同于磁盘文件加数据库的双存储方案，不需要先删文件再删行。

## 12 安全响应头和身份边界

Content-Type 使用 application/octet-stream，Content-Disposition 使用 attachment，并通过 mime.FormatMediaType 编码文件名；浏览器按附件处理，减少上传 HTML/SVG 后被当站内页面执行的风险。

X-Content-Type-Options: nosniff 告诉浏览器不要猜类型；Cache-Control: no-store, private 降低中间缓存保存短期私密文件的机会；Referrer-Policy: no-referrer 避免分享凭证随来源头传播。

这些响应头不是访问控制的替代品。真正的后台权限来自 Bearer key 对 owner 的映射，下载权限来自 share token。用户 B 删除或分享用户 A 的文件返回 404，既不允许操作，也不向 B 明确泄露文件存在性。

当前每个 key 是操作员预先配置的，尚无注册登录、密码恢复、动态 key 吊销管理和审计平台。涉及这些模块时要追加设计与测试，不能在面试中补写不存在的代码。

## 14 七天学习安排

第 1 天：运行 demo，手动上传和创建分享，记录每个请求的状态码。搞清 bytes、UTF-8、JSON、请求头和 URL query 分别存什么。

第 2 天：手画 blobs/files/shares 三张表，解释为什么两个文件名可以共用一份内容。写一段 Go 程序计算 hello 的 SHA-256，修改一个字符观察输出。

第 3 天：重写 Put 和 Stats；补相同内容两次上传测试，删除一个引用后检查统计。解释为何物理内容字节不等于数据库文件大小。

第 4 天：重写 Share；阅读 crypto/rand、sha256、hex，明确 token 只返回一次。给分享列表加一个测试：不出现 raw token。

第 5 天：重写 Consume；先故意做先查再减版本，讨论它可能出现什么竞态，再改为条件更新并通过并发测试。不要把错误实现发布成正确版本。

第 6 天：理解 Delete/Revoke 和外键；补 HEAD、Range 不扣次数的 HTTP 测试，测试数据库出错如何返回。最后运行 go vet 和全部测试。

第 7 天：选一个真实改进，例如按文件名过滤列表或添加分享备注，补权限和边界测试；提交自己的 commit，录下 3 分钟演示并准备下面的追问。

## 15 面试问题与参考回答

### 1 你为什么做这个项目

我希望解决小团队临时文件交接中的重复存储和分享失控问题。项目用去重空间账本展示存储复用，用限次且可撤销的凭证限制后续访问。当前是单机小文件学习实现。

### 2 为什么不用电商或通用网盘

这个场景让我集中学习文件字节、内容哈希、事务、授权凭证和并发扣额度，功能少但能把边界讲清。不要说市场没有类似产品；辨识度来自可演示的组合和实现说明。

### 3 为什么选 SHA-256

希望内容地址有较低碰撞风险且容易跨语言验证。普通非密码学哈希适合散列表，MD5 不适合作为抗恶意碰撞的安全依据。当前不把 hash 当用户权限。

### 4 哈希相同就绝对相同吗

有限长度哈希理论上一定有碰撞。工程中 SHA-256 碰撞可忽略假设适用于这里；如果业务要求进一步防御，可以同长度再逐字节比较、增加碰撞处理分支。当前代码未实现这种分支。

### 5 文件 ID 和 blob hash 为什么分开

文件 ID 代表一个用户的逻辑记录及名字、分享关系；hash 代表内容。两个逻辑文件可以指向同一内容，删除一个不应删掉另一个的内容。

### 6 为什么只在同用户内去重

全局去重会让 deduplicated 响应或统计成为存在性探针，暴露别人是否拥有某份内容。当前使用 owner+hash，牺牲跨用户节省，简化隔离边界。

### 7 这是秒传吗

不是。客户端发送完整 bytes，服务端校验哈希并复用存储。秒传通常需要上传前查询和持有证明协议，不能仅凭哈希给用户增加文件访问权。

### 8 为什么把文件放 SQLite

小文件场景中，BLOB 和元数据能够一个事务提交，避免文件系统与数据库分别提交的崩溃窗口。代价是数据库变大、写串行和读入内存；不适合直接扩展成大规模网盘。

### 9 如果改用 S3/MinIO 怎么办

先上传临时对象，元数据记录 pending，完成后确认 ready；失败任务异步回收孤儿对象，删除可走 outbox/后台重试。需要设计恢复流程，因为数据库事务不能回滚一个已完成的对象存储请求。

### 10 为什么不能相信 Content-Length

请求可以分块发送，字段也可能错误。服务端必须实际限制读取字节数。这里 MaxBytesReader 限制 HTTP，Store 再检查长度，正常大小才进入持久化。

### 11 这是不是流式上传

不是。这里有上限地读入最多 4 MiB，简单且容易测试。若处理大文件，应流式复制、边读边 hash，并限制总量、速率和并发，避免把整份文件装入内存。

### 12 分享凭证有多少随机性

32 个随机字节等于 256 位。十六进制后是 64 字符，只是表示方法改变，熵没有翻倍。random 来自 crypto/rand，而不是 math/rand。

### 13 为什么只存 token 的 SHA-256

数据库泄露时不直接暴露可使用的下载凭证。请求到来时计算摘要后匹配。由于 token 高熵，直接摘要适合这里；用户自选弱密码应使用专门密码哈希算法。

### 14 URL 泄露了还能保护吗

持有 URL 的人可能消费剩余次数，因此 token 泄露就是授权泄露。可立即撤销，过期和额度也限制风险，但已经下载的副本无法追回。TLS 和日志脱敏仍有必要。

### 15 为什么不用 JWT 做下载链接

限次和主动撤销都需要服务端状态。这里直接用随机凭证查数据库即可，JWT 不会自动解决次数扣减和撤销，反而会引入签名密钥管理。

### 16 如何保证限次不超卖

把 remaining>0、未过期、未撤销都写在同一条 UPDATE WHERE 中，并用 RETURNING 判断是否放行。不能先读取 remaining 再在 Go 中判断后减一。

### 17 40 个请求争 3 次意味着什么

本地两个独立数据库句柄、40 个并发调用只有 3 个成功，其他收到 ErrGone。这证明该测试场景下原子额度正确，不代表达到某个 QPS，也不代表经过公网压力测试。

### 18 下载中途断开会退回次数吗

不会。数据库提交后额度就花掉，语义是授权次数。网络完成与否没有可靠的跨端原子提交。若要重新取，可由拥有者另外创建凭证，而不是自动补回造成重用漏洞。

### 19 HEAD 为什么特殊处理

HEAD 只是请求响应头，不应读取业务文件并扣额度。Go GET 路由可能匹配 HEAD，所以 handler 显式拒绝，测试先 HEAD 再 GET 证明没有消耗。

### 20 Range 为什么暂不支持

分段下载会把一次用户下载拆成多个 HTTP 请求。必须先设计会话和次数语义。当前直接 416，并且在 Consume 前判断，避免无效请求扣额度。

### 21 撤销与正在下载同时发生怎么办

数据库写事务决定谁先获得授权。撤销后新授权被拒绝，已完成扣减并读取 bytes 的请求可能仍然发出内容。撤销不是撤回已发送字节。

### 22 删除文件为什么不会误删共享内容

先按 owner 删除逻辑文件，再检查同 owner/hash 是否还有 files 引用；有就保留 blob，没有才删除。所有操作同事务，外键删除 shares。

### 23 配额怎么防并发突破

事务第一条是写操作，再查询总大小和文件数，超限则回滚。其他 writer 不会在配额检查和提交之间插入自己的成功写入。当前配额限制文件内容与条目，分享历史数量的清理策略尚未实现。

### 24 为什么统计下降了数据库还很大

SQLite 删除数据会留下可复用空闲页，WAL 和索引也占空间。统计只反映存活内容；需要离线维护或 VACUUM 才可能回收文件体积，不能在每次删除时都做重维护。

### 25 文件名怎样避免目录穿越

这里不按用户名字写磁盘路径，名字只作元数据，还拒绝斜杠、反斜杠、NUL 和换行。迁移文件系统后仍应通过服务端生成的安全路径写入，不能拼接任意客户端路径。

### 26 Content-Disposition 有什么作用

要求浏览器以附件下载，使用标准库安全格式化文件名；配合 octet-stream 和 nosniff，减少恶意 HTML 当同源页面执行。没有病毒扫描，不能宣称文件内容本身安全。

### 27 用户身份从哪里来

操作员预置 key 映射 owner。客户端提供 Bearer key，服务端通过恒定时间比较校验。不是从 user_id query 或 X-User 直接读身份。项目没实现密码登录。

### 28 哪些数据可能是秘密

API key、原始 share token 和文件内容都要保护。数据库只保存 token 摘要，但 BLOB 未加密；备份也含敏感内容。源码仓库不应提交数据库或真实 key。

### 29 下一步你最想改什么

先增加限流和并发内存上限、分享数量配额与过期记录清理，再按真实需求考虑对象存储。扩展必须加测试，尤其不能为了大文件而无上限地 ReadAll。

### 30 简历如何描述才准确

写“实现用户内 SHA-256 去重与逻辑文件引用分离、可撤销限次分享、条件更新防止额度并发超扣，并用真实 SQLite 和 HTTP 测试验证”。不写分布式存储、分块秒传、端到端加密或百万用户。

## 16 两分钟介绍与验收标准

介绍：我做了一个 Go 临时文件交接服务，重点是相同内容复用和分享权限收回。文件逻辑记录和内容分表，按 owner 加 SHA-256 去重，用事务保证字节、元数据、配额一致。分享 token 使用安全随机数，数据库只存摘要；下载时原子扣次数，同时判断过期和撤销。项目有空间统计与一键演示，测试包括两连接 40 请求争 3 次额度。当前是小文件单机实现，额度按授权请求计算，没有分块上传和对象存储。

现场演示先上传同样内容两次，解释统计；创建一次性分享，展示 200 后 410；创建新分享后撤销，展示拒绝；最后打开并发测试，解释错误实现为什么会多放行。

完成标准：自己实现 Put、Share、Consume；不看稿解释 transaction、hash、owner、token；通过全部测试与 demo；亲手补一个 Range 不扣额度测试或文件过滤功能；能说明至少三项限制。掌握后再在投递简历中展开项目，避免把“读过代码”当成“能维护代码”。
